# 계약서 변경사항 — 1주차 더미 구현 결과

더미 서버를 만들면서 계약서가 정하지 않았거나 모호했던 부분을 채웠습니다.
**전부 추가와 명확화이며, 기존 필드명·타입·의미는 하나도 바꾸지 않았습니다.**

지금 짜고 계신 파싱 코드에 영향이 있는 것만 골라 적었습니다.
원문은 「질문생성 API계약」 8장, 「리포트생성 API계약」 2·6·9장에 반영돼 있습니다.

---

## 파싱 코드를 고쳐야 하는 것

### 1. 에러 본문 형식이 확정됐습니다

계약서에 HTTP 에러 본문 모양이 없었습니다. 폴링 실패 응답과 같은 형태로 통일했습니다.

```json
{
  "error_code": "UNAUTHORIZED",
  "message": "시크릿 헤더가 없거나 올바르지 않습니다"
}
```

```
status는 없습니다      HTTP 상태 코드로 이미 구분되므로 중복
error_code는 null이 안 됩니다   백엔드가 분기하는 기준이므로
{"detail": "..."} 형식은 안 씁니다   문자열 파싱이 필요해져서
```

**모든 4xx · 5xx가 이 형식입니다.** 하나만 파싱하면 됩니다.

### 2. 검증 오류가 422가 아니라 400입니다

FastAPI 기본값이 422인데, 400으로 통일했습니다.
백엔드가 두 가지 형식을 처리하지 않아도 되게 하려는 것입니다.

```
replay_log[].category가 카테고리 8종과 다름   → 400 INVALID_CATEGORY
리포트 answers[] 형식 오류                    → 400 INVALID_ANSWERS
그 외 모든 검증 오류                          → 400 INVALID_REQUEST
```

### 3. `INVALID_REQUEST` 코드가 새로 생겼습니다

계약서에 없던 코드입니다. 일반 검증 오류를 담습니다.

```
persona · question_count 등 값이 허용 범위 밖
필수 필드 누락
retry_of_session_id만 있고 replay_log가 없음
Idempotency-Key 헤더 누락
존재하지 않는 경로 (404 + INVALID_REQUEST)
```

**재시도하지 마세요.** 클라이언트 버그입니다.

### 4. 리포트 요청 `answers[]`에 두 필드가 추가됩니다

```json
{
  "question_id": "q_1",
  "type": "question",
  ...
  "is_replay": false,        ← 추가
  "is_spare_topic": false    ← 추가
}
```

**이유** — 리포트 응답의 `questions[]`가 두 값을 담고, 회차 비교(`/ai/reports/compare`)가
`is_replay`로 비교 대상을 거릅니다. 그런데 AI 서버는 세션을 보관하지 않아
요청으로 받지 않으면 이 값을 알 수 없습니다.

로그 테이블에 이미 저장하고 계신 값이므로 그대로 실어 보내시면 됩니다.

```
안 보내도 요청은 통과합니다      기본값 false
다만 회차 비교가 동작하지 않습니다  by_question이 항상 빈 배열
```

### 5. `content` 축 실패는 리포트가 아예 안 옵니다

**축마다 실패 처리가 다릅니다. 이게 가장 중요합니다.**

```
                status    report_status   axes_failed
content 실패     error     —               —            ← result 자체가 없음
speech 실패      done      partial         ["speech"]
gaze 실패        done      partial         ["gaze"]
```

`content`가 실패하면 이렇게 옵니다.

```json
{
  "status": "error",
  "error_code": "CONTENT_FAILED",
  "message": "내용 분석에 실패해 리포트를 만들지 못했습니다"
}
```

`result`도 `report_status`도 `overall`도 없습니다.
**`status`를 먼저 보고 분기해 주세요.**

내용 관련성이 없으면 적절성 게이트가 작동하지 않아 총점을 신뢰할 수 없기 때문에,
부분 리포트를 만들지 않습니다.

### 6. 축 결과에서 없는 필드가 있습니다

```json
"content": { "status": "ok",      "score": 65, "display": 4, "metrics": {}, "evidence": [] }
"gaze":    { "status": "failed",  "score": null, "display": null, "metrics": null,
             "evidence": [], "error_code": "GAZE_FAILED" }
"gaze":    { "status": "skipped", "score": null, "display": null, "metrics": null,
             "evidence": [], "reason": "no_video" }
```

```
error_code   status가 failed일 때만 있습니다
reason       status가 skipped일 때만 있습니다
```

`ok`인 축에는 두 필드가 **아예 없습니다.** null이 아니라 키가 없습니다.

## 알아두시면 되는 것 (코드 수정 불필요)

### `doc_id`는 RAG 인덱스가 아니라 파싱 캐시입니다

초안에 「RAG 인덱스의 키」라고 적혀 있었는데, 실제로는 벡터 검색을 쓰지 않습니다.
자소서가 6페이지 정도라 잘라서 검색할 이유가 없고, 오히려 통째로 넣는 편이
질문 품질이 좋습니다. 자소서와 프로젝트 이력을 엮어서 묻는 질문이
조각으로 자르면 나오지 않기 때문입니다.

```
필드          그대로 (Optional, 지금은 항상 null)
보내실 값      그대로 (null)
바뀌는 것      계약서 문구뿐입니다
```

**백엔드에서 고치실 것은 없습니다.**
인프라 쪽에서 인덱스 저장용 볼륨을 잡아두셨다면 그건 필요 없습니다.

### `topic_total`이 세션 도중에 늘어납니다

계획된 토픽 수로 시작해서, 답변이 부실해 예비 토픽이 투입되면 늘어납니다.

```
계획 4토픽 세션에서 예비 2개가 투입되면   4 → 5 → 6
```

정확히는 `max(계획된 토픽 수, 지금까지 열린 토픽 수)`입니다.
**진행률에는 쓰지 마세요.** `question_number / question_total`을 쓰시면 됩니다.

### 없는 `task_id`는 404 `SESSION_NOT_FOUND`

작업 전용 코드를 따로 두지 않았습니다.
재시도 없이 세션을 정리해야 하는 상황이라 처리 방식이 같기 때문입니다.

### 재연습 판별

```
question_count가 replay_log와 다르면   → AI가 감지해서 일반 세션으로 처리
persona가 원본과 다르면                → AI가 감지할 수 없습니다
```

`replay_log`에 페르소나 단서가 없어서입니다.
**페르소나를 바꾼 재연습이면 `replay_log`를 보내지 말아주세요.**

### `/health`, `/ready`가 추가됐습니다

시크릿 헤더 없이 호출할 수 있습니다.
컨테이너 헬스체크에 쓰고 있으므로 `depends_on`에
`condition: service_healthy`로 기동 순서를 잡을 수 있습니다.

```
metrics 세부 필드      축별 담당자가 지표 확정 후
축 가중치 0.5/0.3/0.2  앵커 답변 세트 검증 후
게이트 임계 30 · 상한 40   앵커 답변 세트 검증 후
resilience 산출식      압박형 실제 세션 확보 후
```

**전부 값의 문제이며 구조를 바꾸지 않습니다.**
지금 파싱 코드를 만드셔도 됩니다.

## 폴링 루프는 DUMMY_POLL_TICKS로 검증하세요

기본값에서 더미는 **즉시 `done`** 을 반환합니다.
실제 서버는 `processing`을 여러 번 거치므로, 그대로 개발하면
폴링 루프의 `processing` 분기가 한 번도 실행되지 않습니다.

```bash
DUMMY_POLL_TICKS=3 docker compose up -d
```

```
폴링 1회   {"status":"processing","stage":"stt"}
폴링 2회   {"status":"processing","stage":"generating"}
폴링 3회   {"status":"processing","stage":"tts"}
폴링 4회   {"status":"done","result":{...}}
```

리포트는 `stage`가 `transcribing … composing`이고 `progress`가 함께 옵니다.

**`processing`과 `error`에는 `result`가 없습니다.**
`status`를 먼저 보고 분기해 주세요.
